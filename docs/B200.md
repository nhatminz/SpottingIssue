# Chạy client trên B200 với DeepSeek đã serve

Project root mặc định trong `scripts/run_pipeline.sh`:

```text
/workspace/storage-shared/nlp/minhpn19/LegalDataset
```

Đã dùng endpoint và model ID bạn cung cấp cho **cả hai agent**:

```bash
DEEPSEEK_API_BASE=http://172.29.62.173:8000/v1
DEEPSEEK_MODEL=DeepSeek-V4.1-Flash-1017
```

`GEN_API_BASE` / `JUDGE_API_BASE` mặc định lấy từ `DEEPSEEK_API_BASE`; `GEN_MODEL` / `JUDGE_MODEL` lấy từ `DEEPSEEK_MODEL`. Bạn vẫn có thể override từng agent riêng. ID này là tên server nhận trong request, không phải đường dẫn weights. Không cần copy/download model hoặc chạy script serve Qwen/DeepSeek ở phía client.

## GPU và dependencies

**Client không cần GPU, CUDA, PyTorch, vLLM hoặc SGLang.** GPU inference nằm ở server `172.29.62.173`. Client chỉ đọc JSONL, dựng prompt, gọi HTTP, validate, điều phối debate và lưu output/audit/checkpoint. Có thể chạy client trên node CPU nếu node đó truy cập được shared storage và endpoint.

`CUDA_VISIBLE_DEVICES` mặc định rỗng và không chọn được GPU của server. `TOKENIZER_PATH` mặc định rỗng; client không import Transformers khi không dùng tokenizer local. Nếu cần đếm token bằng tokenizer local, chỉ cần tokenizer và dependencies tương ứng trên CPU, không cần weights.

Nếu chưa có Python environment, dùng Python >=3.10:

```bash
cd /workspace/storage-shared/nlp/minhpn19/LegalDataset
python3.11 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -e .
```

Nếu dùng environment đã có sẵn, đặt `PYTHON_BIN=/path/to/environment/bin/python`. Không copy nguyên `.venv` từ máy 3090 sang B200; tạo environment tại đường dẫn mới.

## Workers, concurrency, batch và phạm vi input

| Biến | Default | Ý nghĩa |
| --- | ---: | --- |
| `MAX_WORKERS` | 1 | Số bản án được xử lý đồng thời; mỗi worker giữ một vụ qua toàn bộ debate. Đây là các async tasks, không phải số GPU hay bản sao model. |
| `MAX_CONCURRENT_REQUESTS` | 1 | Tổng HTTP inference requests đang chờ response, tính chung cả Generator và Judge. |
| `BATCH_SIZE` | 8 | Số bản án đưa vào một đợt; chờ cả đợt xong rồi xử lý đợt tiếp theo. Đây không phải GPU batch của server. |
| `START_INDEX` | 0 | Index bản ghi input bắt đầu inference, tính từ 0. Giá trị 100 là bản ghi thứ 101. |
| `LIMIT` | 0 | Số bản ghi input được chọn từ START_INDEX; 0 nghĩa là đến cuối file. Không phải số bản án PASS cần thu được. |

Ví dụ `START_INDEX=100 LIMIT=50` chọn các bản ghi input có index 100–149, tức thứ tự 101–150. Bản án bị REJECTED hoặc FAILED vẫn được tính vào 50 bản ghi đã chọn.

Trong một vụ, Generator và Judge chạy lần lượt. Do đó số requests đang chạy tối đa bị chặn bởi `min(MAX_WORKERS, MAX_CONCURRENT_REQUESTS, BATCH_SIZE)` và còn tùy số record/cache còn lại. Đặt `MAX_CONCURRENT_REQUESTS=16` nhưng `MAX_WORKERS=1` vẫn chỉ có tối đa một request inference tại một thời điểm. Nên để BATCH_SIZE >= MAX_WORKERS nếu muốn tận dụng workers.

Ví dụ cấu hình gửi tối đa 4 requests đồng thời, nếu server cho phép:

```bash
MAX_WORKERS=4 MAX_CONCURRENT_REQUESTS=4 BATCH_SIZE=8 \
bash scripts/run_pipeline.sh
```

Các con số này chỉ điều khiển tải HTTP của client; không tự thay cấu hình phục vụ của B200. Khi resume cùng phạm vi, checkpoint tự bỏ qua COMPLETED/REJECTED; không cần tự tăng START_INDEX.

`ENABLE_BLIND_JUDGE_DISCOVERY=true` mặc định. Mỗi vụ chạy Stage A chỉ với situation trước, rồi Generator, rồi Stage B dùng nguồn đầy đủ. Nếu PASS ngay, đây là 3 requests độc lập. Rubric/scope mới và cách tạo run mới để tránh dùng lại PASS cũ được mô tả trong [strict_scope.md](strict_scope.md).

## Output budget và context budget

| Biến | Default | Giới hạn |
| --- | ---: | --- |
| `GEN_MAX_OUTPUT_TOKENS` | 131073 | Token sinh mới tối đa cho **mỗi request Generator**, gửi tới API bằng `max_tokens`. |
| `JUDGE_MAX_OUTPUT_TOKENS` | 131073 | Token sinh mới tối đa cho **mỗi request Judge**. |
| `MAX_INPUT_TOKENS` | 100000 | Trần toàn bộ prompt đầu vào, gồm system prompt, JSON schema, nguồn được phép và lịch sử trao đổi. |
| `MAX_CONTEXT_TOKENS` | 262144 | Trần input + output budget cho **từng request**, dùng để kiểm tra ở phía client. |

Với từng agent, pipeline kiểm tra:

```text
input_tokens <= MAX_INPUT_TOKENS
input_tokens + output_budget_của_agent <= MAX_CONTEXT_TOKENS
```

Ví dụ một request Judge có input 20.000 tokens và `JUDGE_MAX_OUTPUT_TOKENS=131073` thì cần ngân sách context ít nhất 151.073 tokens. Hai agent có request/context riêng: không cộng `GEN_MAX_OUTPUT_TOKENS + JUDGE_MAX_OUTPUT_TOKENS` thành một context chung. **Mỗi lượt Generator có tối đa 131073 token sinh mới, và mỗi lượt Judge cũng có riêng tối đa 131073 token sinh mới.** Không chia số token này cho các vòng và không trừ số token đã sử dụng ở request trước; request ban đầu, revision/rebuttal, final evaluation và JSON repair đều dùng budget tương ứng của agent.

Với thinking, phần reasoning cũng sử dụng budget sinh token theo backend; cần chừa đủ cho JSON cuối cùng. Hết budget có thể khiến API trả `finish_reason=length`; pipeline coi đây là FAILED, không xuất labels dở dang. API DeepSeek định nghĩa giới hạn completion và tổng input/output trong [Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/).

**MAX_CONTEXT_TOKENS chỉ là guard của client, không tăng context thực trên server.** Giá trị 262144 chừa chỗ cho tối đa 100000 input + 131073 output trong một request; đây không phải khẳng định giới hạn thật của server 1017. Server phải cho phép `max_tokens=131073` và context đủ chứa input + output. Nếu server chỉ cho sinh tối đa 131072 tokens thì mức 131073 bạn yêu cầu sẽ bị server từ chối; pipeline không âm thầm giảm xuống. Khi không có TOKENIZER_PATH, client dùng upper bound từ UTF-8 bytes nên có thể từ chối sớm hơn đếm tokenizer thực.
